# Hot-patch channel — Clear, but review before building

**Date:** 2026-11-20.
**Owner:** we.
**Goal:** small app changes reach clinics as hot patches (no CI round-trip) —
applied as new files + webview reload, while the full installer path
(`update-manifest.json` → NSIS installer) stays for bigger changes.

---

## 1. What is being asked for

"We ship small updates without the CI + GitHub installer dance."

Facts that shape it (all checked against the tree):

- Desktop app = Tauri v2; the webview serves `dist/` (`frontendDist: "../dist"`) — assets are plain files the app dir.
- App identity: two version strings — JS: `currentVersion()` = `__APP_VERSION__` (Vite `define`, from `package.json`, `vite.config.ts`); native: `package_info().version` (Tauri, from `tauri.conf.json`/Cargo). A JS-only patch can move the JS one without rebuilding native.
- Existing update path: `checkForUpdates` (manifest → `update_install` NSIS installer) + `update_apply` + `update_diagnostics`.

## 2. The patch mechanism (chosen shape)

`update-patch.json` lives on **gh-pages** next to `update-manifest.json`, served by the same raw URL the app already fetches. One patch per version chain.

### Manifest

```json
{
  "magic": "DENTALUPDATE-PATCH",
  "base_version": "2.31.34",      // the running app version the patch targets (TS gate)
  "display_version": "2.31.35",   // shown in panel on success; JS identity moves on next patch
  "released_at": "2026-11-20T21:00:00Z",
  "notes": "Aligner form small fixes",
  "files": [ { "path": "assets/index-ABC123.js", "sha256": "<64hex>", "size": 366408 }, ... ]
}
```

- `files`: full snapshot of `dist/` (every file with hash+size). Changed chunks get new hashed names → small diffs. `path` is relative to the app dir; application confines it under `<app_dir>/dist/`.
- Deletions (`v2`): optional `deleted: []`; apply deletes them (confined). Not in v1 spec scope — the packer still writes them.
- Version gates (see §4): `base_version` is the contract for both TS (`currentVersion()`) and Rust (identity).

### Discovery (`checkPatch`)

Runs at boot and via the manual check button, like today's check:

- fetch `https://raw.githubusercontent.com/beingadil/Dental-Clinic-Management/gh-pages/update-patch.json` (quietFetch, no cache);
- return `none | available | failed` — `available` = manifest + gate pass + any file.
- Patch wins over installer path when both exist (installer = next big change).

### Apply (`apply_app_patch` — new Rust command)

```
Rust: apply_app_patch(manifest_url) -> Result<AppPatchOutcome, String>
```

1. `app_dir()`: registry InstallLocation (HKU Uninstall/Dental Solutions, same
   story as `installed_relaunch_target`) with `current_exe().parent()` fallback.
2. Fetch manifest via `fetch_text` — add `raw.githubusercontent.com` to
   `TRUSTED_UPDATE_HOSTS`. Validate `magic` + `base_version == package_info().version`.
3. For each file in manifest (resolve host per file — same allowlist):
   canonicalize, require confined under `app_dir()/dist/`, write tmp → rename
   (same pattern as `save_file_bytes`), then re-hash the file and require
   equality with the manifest `sha256` — fail closed on mismatch.
   `deleted[]`: same confinement; remove.
4. Emit progress events (`app_patch://progress`: downloading → verifying → applying).
5. After all verified: `window.eval("location.reload()")` so the webview
   serves the new bundle. (If no window access, return `applied` and TS asks.)

Fail-closed: any fetch error, hash mismatch, bad path, or base mismatch →
`Err`, no partial writes (verify-then-write).

### TS side

- `PatchStatus`:
  ```ts
  type PatchStatus =
    | { state: 'none' }
    | { state: 'available'; display_version: string; notes?: string; released_at?: string }
    | { state: 'applying'; }
    | { state: 'applied'; display_version: string }
    | { state: 'failed'; message: string };
  ```
- `updateService.fetchPatchManifest()` + `checkPatch()`.
- `updateInstaller.ts`: new phases `patch_ready_to_apply` → `patch_applying` →
  `patched`. `applyPatch()` invokes `apply_app_patch` and sets `patched`
  (TS knows the result; the webview reloads — restored as `patched`).
  Boot: `reconcilePatch()` records history.
- `updateHistory`: new events — `patch_available` (as logged at discovery,
  like today), `patch_ready_to_apply` (maybe not needed — keeps ready semantics),
  `patch_applied`, `patch_failed`.
- Panel UX: inline + floating cards, one-click **"Apply Patch"** button (user's answer), `patched` notice; a "Check for updates" button still triggers full check; discover point = every boot + manual.
- Panel behavior v1: only offer when nothing is running (`ready_to_apply`/`applying` guard analog: don't let patch flow clash with installer staging).

### Packer — `scripts/make-app-patch.mjs`

```
node scripts/make-app-patch.mjs [--base 2.31.34] [--out update-patch.json]
```
- Reads `dist/` (run `npm run build` first), writes `update-patch.json` with
  `files: [{path, sha256, size}]` + `deleted: []` + `display_version` + `base_version` (from `--base`, default `package.json`'s version — and documented: the working tree must be built from the same source the running app is; don't use for app version bumps the installer owns).
- Does **not** push (manual) — prints the branch to push.
- `npm test` entry: script unit tests (file-set diff, JSON shape, tampering detection — deny files outside `dist/`?).

### Delivery — manual (user's choice)

`git push origin master:gh-pages` (from a checkout of the branch that holds update-patch.json — note: **the repo does not have a gh-pages branch locally right now; GitHub Pages is not enabled; the branch is managed on origin**). Tell the operator: push `origin/gh-pages` → patch is live. Honestly note: patches are published only by pushing directly — the "review" for a patch = run the script, eyeball the file table (it's printed — changed chunks + count of app files), push. We add CI for patch publication later if ever — v1 out of scope (they asked for no CI).

### Testing / live E2E

- TS unit tests: manifest parse/gate, TS state machine transitions (none→available→applying→patched), tamper: manifest points at a file outside dist → refused by Rust (see below).
- Rust unit tests (`cargo test --lib`): manifest parse+magic+base-gate; path-confinement rejections (traversal, absolute, symlink out); hash-after-write tamper failure; apply runs end-to-end against `app_dir()` in a temp directory + reload is stubbed.
- Live E2E plan: build the app; spawn `dental-solutions.exe` headless; verify "Apply Patch" button exists when no patch (none), and that a patched bundle file set applied from a fixture manifest lands in the app dir (can't test against a real install layout without a patch for it).
- CI: stays as is (no installer flow changes).

### Edge cases & refusal reasons (documented, surfaced on apply failure)

- No app running / desktop-only: nothing discoverable — manifest says `none`.
- Base mismatch: app version changed since manifest — ignore manifest (it'd otherwise be stale), message in `available` as none? The manifest remains — a future app with matching base picks it up.
- Tampered file / missing manifest field: `Err("...hash mismatch, patch rejected...")`.
- The app is mid-work on another feature on the desktop app: reload on apply = disruption — accepted per user choice (same as any update today — data loss on reload — document it).
- Future direction (v2): `deleted` support is wired but unused by default packer; `app_version` display.

### What's in scope of this release's scope

Phase A (this spec) → Phase B (`scripts/make-app-patch.mjs` + tests) → Phase C (`app_patch.rs` + Rust tests) → Phase D (TS states + panel) → Phase E (E2E against a live fixture; docs `docs/app-patch.md` for operators with the publish command) → Phase F (first patch).

### Done when

1. `npm run lint && npm test && cargo test --lib` all green.
2. `docs/app-patch.md` documents the flow; pushed to master, unreleased (this release is #2's "hot-patch channel" preview, no new installer).
3. Live preview walkthrough of the Apply Patch button state + a tamper rejection unit.

### Notes

- Versions: the working tree keeps package.json/tauri.conf at 2.31.34 — no new installer needed for v1. A future installer releases move identity; patches don't change identity.
- Confirmed trust model: manifest served by the same `update-manifest.json` host allowlist extension; per-file hashes are the primary integrity check (hashes computed by us, stored on gh-pages — same trust class as the release metadata, i.e., as strong as today's SHA256SUMS chain).
- We suggest this as the road to v2.31.35-style JS-only changes without CI round-trips.
